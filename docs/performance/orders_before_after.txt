============================================================
INTERPRETATION
==============

Before the index, PostgreSQL performed a sequential scan of the
orders table and then used a Sort operation to order the matching
rows by created_at DESC.

After the composite index was available, PostgreSQL could use an
Index Scan through idx_orders_customer_created. The index contains
customer_id followed by created_at DESC, matching the filtering
and ordering requirements of the query. The resulting plan has no
explicit Sort node.

The measured execution time in this small demo dataset was
0.058 ms before the index and 0.074 ms after the index. The
indexed plan was not faster in this particular tiny dataset.
This is expected because the table contains only a very small
number of rows, so sequential scanning is inexpensive.

The purpose of this benchmark is therefore to demonstrate the
change in PostgreSQL's execution strategy and provide raw
EXPLAIN (ANALYZE, BUFFERS) evidence. With a substantially larger
orders table, the composite index can reduce the amount of data
that PostgreSQL must scan and can provide rows in the requested
created_at DESC order without a separate Sort operation.
